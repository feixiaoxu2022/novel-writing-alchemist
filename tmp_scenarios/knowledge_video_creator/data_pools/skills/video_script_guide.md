# 技术教程视频脚本写作指南

## 一、技术视频的核心挑战

技术教程视频和普通技术博客/文档的本质区别：

1. **时间线性**：观众必须按顺序观看，不能像文档那样跳着读
2. **认知负荷**：视频每秒都在推进，观众没有时间停下来消化
3. **注意力衰减**：前2分钟是黄金时间，之后注意力快速下降
4. **多通道传递**：声音+画面+文字同时传递信息，需要协调

## 二、脚本结构：问题驱动的叙事弧线

### 2.1 每集的基本结构

```
开场钩子（30秒）
  → "你有没有遇到过这个问题？" / "如果我告诉你..."
  
问题定义（1-2分钟）
  → 明确本集要解决什么问题，为什么重要
  
核心内容（5-15分钟）
  → 分3-5个知识块，每块有"概念→例子→要点"的完整循环
  
总结回顾（1-2分钟）
  → 本集要点、关键takeaway

下集预告（30秒）
  → 承上启下，制造期待
```

### 2.2 知识块的内部结构

每个知识块遵循"为什么→是什么→怎么用"的三段论：

```
为什么需要这个概念？（动机/痛点）
  ↓
这个概念是什么？（定义/原理）
  ↓
怎么用？（实例/代码/对比）
  ↓
关键要点（一句话总结）
```

**反面案例**：直接列知识点——"接下来讲A，A是xxx；然后讲B，B是xxx"——这是读PPT不是做视频。

### 2.3 过渡的艺术

知识块之间需要自然的过渡，不能硬切：

**好的过渡**：
- "刚才我们解决了X问题，但你可能会想——如果Y情况呢？这就引出了..."
- "理解了基础概念后，我们来看一个实际案例，看看它在真实项目中是怎么用的"
- "到这里你可能觉得已经够了，但有一个陷阱很多人会踩——"

**差的过渡**：
- "接下来我们讲第二个知识点"
- "下面介绍另一个概念"
- 无过渡直接跳到下一个主题

## 三、口播文字的写作原则

### 3.1 口语化

技术视频的口播必须是"说"出来的语言，不是"写"出来的：

| 书面语（禁止） | 口语（推荐） |
|-------------|-----------|
| 综上所述 | 所以你看 |
| 由此可见 | 这就说明 |
| 在此基础上 | 有了这个之后 |
| 需要指出的是 | 这里有个要注意的 |
| 本文将从...方面 | 我们先看...然后再看... |

### 3.2 节奏控制

- **短句为主**：每句话不超过20个字
- **停顿标记**：在需要观众消化的地方标注[停顿]
- **重复强调**：关键概念用不同方式说两遍（先简单说，再精确说）
- **语气变化**：用问句打破单调("这合理吗？"、"你觉得呢？")

### 3.3 比喻和类比

将抽象技术概念映射到日常经验：

**好的比喻特征**：
- 映射关系清晰（A的X特征 ↔ B的Y特征）
- 观众一定熟悉比喻对象
- 能解释核心机制，不只是表面相似

**示例**：
- "缓存就像你桌上的便签本——常用的信息写在便签上随手看，不用每次都翻字典"
- "微服务架构像一个分工明确的团队——每个人负责一小块，通过消息传递协作"

**警告**：比喻如果不准确，比没有比喻更有害。宁可不用比喻也不要用错误的比喻。

## 四、PPT画面描述（visual_description）的写作原则

脚本中每个segment的 `visual_description` 直接指导PPT制作。写好这个字段决定了最终PPT质量。

### 4.1 画面描述必须具体到PPT文字内容

**差的画面描述**："PPT对比表：四维能力维度对比"
→ 太抽象，Agent制作PPT时会自行发挥，容易写出英文变量名堆砌的内容

**好的画面描述**："PPT左右分栏对比。左侧标题'通用维度'，列出'格式合规——输出格式符合规范'、'业务规则——遵循创作指令和约束'。右侧标题'差异化维度'，列出'内容质量——一创查人物/情感/叙事，二创新增选材/连贯/可生产性'。推荐项绿色勾标注。"
→ 具体到文字内容，Agent照此制作即可

### 4.2 画面描述中的语言要求

- 描述PPT文字内容时必须使用中文，不要出现英文变量名
- 如果某个segment涉及技术术语，在画面描述中就要写好中文翻译
- 公式类内容，在画面描述中直接写出中文化后的表达方式

### 4.3 代码/公式类画面的特殊处理

当口播讲到代码或公式时，PPT上不应该只是贴代码截图。应该：
1. 用中文标注版本替代英文代码（变量名→中文含义）
2. 如果确实需要展示代码（如Python/YAML示例），在画面描述中明确标注"代码展示页"，并注明必须添加中文注释
3. 整个视频的PPT中，代码展示页最多2页

## 五、教学节奏设计

### 5.1 难度曲线

理想的难度曲线是"阶梯式上升"：

```
难度
 ↑
 │         ┌──┐
 │      ┌──┘  │
 │   ┌──┘     │  ← 每个台阶内相对平稳
 │┌──┘        │     台阶间有明确的"升级提示"
 └────────────→ 时间
```

**错误模式**：
- 一路平缓（太简单，无收获感）
- 突然陡峭（断崖式升难度，观众跟不上）
- 忽高忽低（混乱的难度波动）

### 5.2 "3-2-1"节奏法则

- 每**3分钟**必须有一个"价值点"（让观众觉得"学到了"）
- 每**2个**抽象概念之后必须跟一个**具体例子**
- 每**1集**结尾给出**一个**可以立即实践的行动项

### 5.3 前置知识管理

**绝对禁止**：使用观众不可能知道的术语且不解释。

**正确做法**：
- 首次出现专业术语时给出简短解释
- 如果术语在之前的集里讲过，用"我们在第X集讲过的Y"提醒
- 如果概念太复杂不能在本集展开，明确说"这个概念我们会在第X集详细讲"

## 六、系列规划的知识图谱方法

### 6.1 概念依赖分析

```
Step 1: 列出所有需要讲的概念（15-30个）
Step 2: 画依赖图——学A之前必须先学B
Step 3: 拓扑排序——确定讲解顺序
Step 4: 分组打包——相关概念放同一集
Step 5: 难度校准——每集难度逐步递增
```

### 6.2 每集的"收益承诺"

每集标题和开场必须给观众一个明确的"收益承诺"：

**好的收益承诺**：
- "看完这集，你就能自己设计一个评价体系"
- "这集讲完，你会理解为什么90%的检查项设计是无效的"

**差的收益承诺**：
- "这集介绍评价体系的基本概念"
- "本集讲解Checker的实现"
